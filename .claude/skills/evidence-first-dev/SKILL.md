# 証拠ファースト開発 — 進め方の型

どのモデルで動いていても、この順序を守ると成果物の質が安定する。

## 1. 書く前に読む

- 修正・追加の前に、**該当コードを grep で特定して実際に読む**。推測で書き始めない
- 既存の類似機能・休眠コードを探す。「廃止済みだが残っている関数」が
  そのまま再利用できることがある (例: 廃止された引継ぎ関数をテストシーズン用に転用)
- 慣習はコードベースから学ぶ: 命名、エラー処理、コメント密度、既存のフォールバックパターンを
  真似る。自分の流儀を持ち込まない

## 2. メカニズムで語る

- バグ修正では「どの仕様がどう作用して症状が出たか」を特定してから直す。
  症状へのパッチ (とりあえず overflow:hidden 等) だけで済ませない
- 例: 「1fr は min-content より縮まない → グリッドが画面幅を超える → ページが横にガタつき
  スワイプ判定と競合」— ここまで言えて初めて正しい修正 (minmax(0,1fr)) が選べる
- ユーザーへの説明にもメカニズムを1段含める。納得と再発防止につながる

## 3. 曖昧な報告への対応

「違和感がある」「なんかおかしい」と言われたら:
- まず自分で仮説を立てて**再現条件をコードから逆算**する
- 特定できなければ「どのタブ・どの操作・どのタイミングか」を具体的に聞く。
  ただし聞く前に自力で1回は絞り込む

## 4. 変更の設計

- 同じ情報を複数の出口 (画面表示と画像出力など) に出すときは、
  **共通のデータモデル関数**を1つ作って両方に消費させる。ロジックを二重に書かない
- 機能を消すときは中途半端に残さない。参照が0件になったことを grep で確認する
- 破壊的操作 (データクリア等) には必ず復元経路 (スナップショット/バックアップ) を先に用意する

## 5. 正直に報告する

- 「テストが通った」と「実機で動く」は別物。**何を検証済みで何が未検証か**を分けて伝える
- 設計規約から外れた判断をしたら、指摘される前に自分から明示する
  (例: 「このボタンの緑グラデはガイドに無い拡張です。黒に変えることもできます」)
- 完了報告には「ユーザーが次にやるべきこと」(適用SQL、実機確認のチェックリスト) を必ず添える

## 6. 出荷前チェック

- 構文チェック・テストを全部回す (プロジェクトの verify 手順があればそれに従う)
- コミットメッセージに「何を・なぜ」を残す。動機は履歴にしか残らない
- push 前に diff を見て、意図しない変更が混ざっていないか確認する
