2026-10-22 に職場 PC の一時領域で回した実験を、どの PC でも動くように移したもの。
本物のソルバー (`js/optimal-plan.js`) と本物のブロック定義 (`js/domain/raidBlocks.js`)、
第44回の実データ (`data/2026-09.json`・30 人) で、本番のブロック制の流れ
(各ブロックの頭に「そのブロックに出られる人」だけで残りの 1 日を組み、そのブロックの凸だけ実行する) を回す。

単体テストではない (`run-all` には入れない)。ソルバーやブロック制の方針を変えるときに流して、数字を見比べる。

```sh
node tests/bench-blockflow/multi-block.mjs
node tests/bench-blockflow/carry-over.mjs
BENCH_N=40 node tests/bench-blockflow/boss5-two-teams.mjs            # いまの強さ

```

`BENCH_N` は盤面の数 (既定 40。1 盤面でソルバーを 7 回解くので、40 だと数分)。`SCALE` は全員のダメージの倍率。

## 2026-10-22 の結論 (ユーザー決定の根拠)

- **離れたブロックの人**: 朝のブロックで組むと、凸先がある限り 3 凸とも朝に入る。凸先が無い凸は置かれず、夕方のブロックで拾われる (温存される)。
  → 「朝 1・夕方 2」を通すには時間アンケートの凸数が要る (段階 2a で聞けるようにした・2b でソルバーの上限にする)
- **「後ろのブロックにも出られる人の優先度を下げる」は入れない**: ソルバーの写しに罰の項を足して測ったが、残る凸は変わらなかった
  (残るのは Lv4 のボス 5 の編成不足が原因)。試作 (ソルバーの写し) はリポジトリに入れていない
- **遅い時間の人はボス 5 の 2 編成**: Lv4 が開く強さ (SCALE=1.3) では残る凸 18 → 1・与ダメ +20%。
  ただし Lv4 が開かない強さ (×1) では 2 編成目が Lv3 のボス 5 を先に倒してしまい逆効果
  → 段階 5 でソルバーに「2 編成目は Lv4 が開く見込みのときだけ使う」の手当てが要る

## 2026-10-23 段階 5 の手当て (secondB5Lv4Only = ボス 5 の弱点の編成②は Lv4 だけ)

`BENCH_N=40` (×1 / ×1.3)。残った凸 / 与ダメの平均:

| 強さ | 時間帯 | 方針なし | 2 編成 (手当てなし) | 2 編成 + 手当て |
|---|---|---|---|---|
| ×1 (Lv4 が開かない) | 夜に集中 | 1.0 / 2973B | 5.6 / 2842B | 3.5 / 2909B |
| ×1 | 散らばり | 1.9 / 2944B | 4.9 / 2837B | 3.3 / 2893B |
| ×1.3 (Lv4 が開く) | 夜に集中 | 14.4 / 3295B | 0.5 / 3796B | 0.9 / 3774B |
| ×1.3 | 散らばり | 13.3 / 3270B | 5.8 / 3551B | 4.8 / 3589B |

手当てで ×1 の悪化が半分ほどになり、×1.3 の効果はほぼ残る。×1 に残る悪化は、ベンチがボス 5 の模擬を持っていない人に 1 編成目まで足しているため
(本番は 5 属性の模擬が前提で、足されるのは 2 編成目だけ)。→ 画面の算出と承認の影響で常に `secondB5Lv4Only: true` を渡す
