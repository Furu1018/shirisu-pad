## 2. 段階 2: 時間アンケートの凸数 + 隙間型の撤廃 (SQL 53)

- **データ**: `availability_confirmations` に `block_counts JSONB` (例 `{"5-8":1,"18-20":2}` — 鍵はブロックの `from-to`。区切りが変わっても読める)。
  SQL 53 = `ALTER TABLE availability_confirmations ADD COLUMN IF NOT EXISTS block_counts JSONB` + 99 の判定行。未適用は従来どおり (凸数なし)
- **画面 (メンバー)**: 時間のシート (③-b) の ON のブロックに「− N 凸 +」。合計 3 まで (超えたら他を減らす案内)。入れなければ null (= 運営任せ)。
  ホームの帯の下に「朝 1 · 夕方 2」。隙間型のチェックは**消す** (列 `players.flex_time` は残し、読まない・書かない。既存の true は無視)
- **画面 (運営)**: 👥 メンバー状況に「凸数の希望」列。時間未登録の人は「時間未登録 (催促)」で、**候補にしない** (いつでも可、にしない)
- **ソルバー** (`js/optimal-plan.js`): `players[].blockCaps = [{ fromIdx, toIdx, max }]`。候補列挙で「その時刻のブロックの置いた数 ≥ max」なら置かない
  (貪欲・予約・sticky・修復パス すべて `applyPick` の前の 1 か所で判定)。ブロックで組むときは、そのブロックの cap − 済みの数 がその人の残り凸の上限。
  `flexTime` は読まない (`hourIdxs === null` の「いつでも」は時間未登録だけ → 候補から外す。未登録の人は `membersTimeUnknown` に出す)。
  指紋: cap を渡さない・flexTime を渡さない盤面は不変であること。ベンチ `bench-block.mjs` に cap つきの案を 1 本足す
- **予約**: `time_mode='flex'` の申請は作れなくする (申請シートから ⏳ を消す。既存行は読める)
- テスト: 単体 (cap の各経路・未登録の扱い)・`avail-save.mjs` (凸数の保存)・変異
- ふるりがやること: **SQL 53 を SQL Editor で実行** (push のあとに案内する)

## 3. 段階 3: 予約をブロックで (SQL 54)

- **データ**: `plan_reservations.time_mode` に `'block'` を足し、`block_from INT` / `block_to INT` (時・含む) を足す。CHECK: block のとき time_slot NULL・from/to あり。
  SQL 54 = ALTER + CHECK の張り替え + 45/47 のトリガー/RPC の `time_mode` の扱い (block を fixed と同じ扱い = 固定の約束)。`js/practice/server.js` も同期
- **ソルバー**: 予約の `window = { fromIdx, toIdx }`。置く時刻は「窓の中で、レベルが開いたあとの最も早い時刻」(`earliestHourFor` を窓で絞る)。
  窓の中にそのボスがいるレベルが無ければ `no_boss_at_time` (理由の文は「約束の時間帯には…」)。`resolveReservationLevels` は窓の頭で判定し、置けなければ窓の中を順に試す。
  未達の突き合わせは「窓の中に置かれた」で満たす
- **画面 (メンバー)**: 申請シート = ① 出られるブロックから 1 つ ② 登録済みの模擬から PT (行き先のボスは PT で決まる) → 「夕方 (18〜20時) に 風圧PT 編成① で B3 へ」。
  申請の導線 `[data-member-resv]` は lite でも出す (`[data-member-input]` と分ける)。ホームの 3 枠・「わたしの凸」・予約の欄は「夕方 のどこか」と出す
- **画面 (運営)**: 承認の影響・承認ダイアログ・時間割のチップ (窓の表示)・📌 は従来どおり時刻つき (運営が置くのは時刻)
- テスト: 単体 (窓の置き方・理由)・`home-slots.mjs`・配線・SQL と JS の遷移表の突き合わせ・練習 (偽サーバ) ・変異
- ふるりがやること: **SQL 54 を実行**

## 4. 段階 4: 運営の結果の取り込み + 配信の通知

> **実装済み (2026-10-23)**。設計からの変更: ①「凸していない」は新しい表 (SQL 55) を作らず `raid_event_notices` の kind `atk_skip` に置いた (疎通確認と同じ・ふるりの SQL 作業なし)。
> ②「📥 取り込む」はファイル選択を開かず、その人・そのボス・割当の編成の下書きをすぐ出す (ダメージを入れるか 📷 で読む)。
> ③ 突き合わせは「配信を算出した時刻より前の凸は照合しない」で前のブロックの凸を外す (取り込んだ凸の時刻は登録した時刻なので、時刻でブロックを決めない)。
> ④ 配信の通知は L4 (割当が変わりました) と重ねない。同じブロックの配信し直しは変わった人だけ。

- **結果の取り込み** (戦況タブ「📥 結果の取り込み」・当日と終了): スクショを選ぶ/落とす → 既存の凸報告 OCR (`_ocrAttackMultiAndMerge`) で ボス・ダメージ を読む →
  「誰の凸か」(投稿者名の対応表 `players.discord_name` は**持たない** — 運営が選ぶ。直前に選んだ人を既定) → 使った PT は**その人の模擬のうち、そのボスの弱点属性**
  (2 編成なら選ぶ・配信どおりなら既定) → `report_attack` RPC に `reported_by = 運営` で登録 (= 既存の代理凸の経路 `openOpsProxyAttackModal` を**この画面に統合**)。
  登録で残 HP が減り (既存)、本人のホームが「済」になる (既存の `homeSlots` の done)。
- **報告の無い凸** (③-f の「予定の時刻を過ぎた未報告」を拡張): 行に「Discord で聞く」(文面をコピー) と「凸していない」(= `attack_check_skips` に残す: season_id, player_id, plan_key, by, at。
  SQL 55。次のブロックの残り凸に戻す = 何も登録しない、を明示するだけ。盤面には影響しない)
- **次のブロックを組む前の片付け**: 条件パネルの頭に「未登録のリザルト N 件・報告の無い凸 M 凸」(あるときだけ・赤) と「結果の取り込みへ ›」。止めはしない (運営の判断)
- **配信の通知** (h): ブロックのぶんの配信は、**そのブロックに割当のある人**へ「🧱 夜 21〜23時 のぶんが配信されました — 21時 B3 風圧PT 編成①」(1 通に自分の凸を書く)。
  既存の「🔄 あなたの割当が変わりました」(L4・差分の人だけ) は、初回配信の人にも出すよう `planDiff` の added を通知対象にする。重複は `raid_event_notices` の kind `block_publish` / ref `<plan id>:<player>` で防ぐ
- テスト: 取り込みの実行テスト (偽サーバで RPC まで)・通知の宛先 (`practice.mjs` の型)・変異
- ふるりがやること: **SQL 55 を実行** / Discord に結果用のチャンネル (#凸報告) を用意し、メンバーに「凸したらリザルトのスクショを貼る」と周知
