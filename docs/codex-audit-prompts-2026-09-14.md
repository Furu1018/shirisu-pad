# 監査の主題: 「1人3凸」という**唯一の希少資源**を、4つの仕組みが奪い合っている

ユニオンレイドでは 1人が1日に3回しか凸(攻撃)できません。この3枠を、次の4つが別々に押さえます。

1. **実凸** (`attacks` テーブル) — 実際に攻撃して報告した記録。確定
2. **予約** (`plan_reservations`、SQL 39/40/42/45) — status が
   `requested`(本人の申請) / `approved`(約束・🔒) / `cancel_requested` / `pinned`(運営の下書き・📌) /
   `fulfilled` / `released` / `rejected`
3. **締め凸依頼** (`finish_requests`、SQL 36/44) — 「このボスを締めてほしい」という打診。
   status が pending / accepted など。SQL 44 で**複数案の同時打診** (offer_id / plan_key / deadline_at) が入った
4. **配信されたプラン** (`published_plans`、SQL 38) — 運営が配った時間割。予約を焼き込む

★ ここが核心: **枠の数え方が場所ごとに違います**。
- SQL 39 の容量トリガ / SQL 42 の部分一意索引 / SQL 40 の凸報告 RPC は
  `('requested','approved','cancel_requested')` を数える (**pinned は数えない**)
- SQL 45 の `plan_reservations_pin_check` トリガは

   - 📌 の `ask_deadline_at` は「過ぎても自動で外さない」と 45 に書いてある。溜まり続けないか

   - `cancel_requested (承認済み起点) → approved` (取り消し希望を運営が却下して約束に戻す) のとき
   - `TG_OP = 'UPDATE' AND OLD.status = NEW.status` の早期 return が、approved のまま player_id を変える等の経路を素通しにしないか
   - 39 の容量トリガ (requested/approved/cancel_requested を数える) と 47 (approved/pinned を数える) が**両方**走る順序で、
     どちらかが通してどちらかが落とす組み合わせに矛盾は無いか。approved の INSERT で 39 が「requested 3 件 + 1」で落とす一方、
     47 は通す、のような「期待と違う側が落とす」ケース
   - `pinned → approved` で NEW.id が自分自身: 45 の一意索引 uq_plan_reservations_pin_card との整合
B. **同じカードの 📌 の除外**が抜け道にならないか: 運営が同じカードに 📌 を置き、本人がそのカードを申請し、運営が承認する — 除外のせいで
   承認時に 📌 が数えられず、承認直後に _resvTransition が 📌 を superseded で外す前に**別の運営が別の 📌 を置く**と 4 件になるか。
   その 4 件目は 47 (pinned の INSERT) が数えるので落ちるはず — 確認を。
C. **締め凸の了承の順序変更**の副作用: 「枠を取ってから伝える」で、
   - 予約 INSERT が成功 → respond が「すでに返答済み」で失敗 → released で返す、のとき 39 の status_via_rpc トリガ
     (承認済み以降の内容変更禁止) に引っかからないか (released への遷移は RPC 経由なので通るはず)
   - respond が成功したのに、その後の _refreshFinishRequests / renderMyReservations で古い応答が来る経路
   - 本人が 2 タブで同時に「了承」: 両方が canApprove を通り、両方が INSERT → 39/47 のトリガと 42 の一意索引で片方が落ちる →
     落ちた側は respond を呼ばない (正しい)。通った側だけ accepted になる。**この理解で合っているか**
   - `mine.some(isActive && 同じボス)` → { why: 'exists' } で respond に進む: このとき既存の予約が `requested` (未承認) だと
     「了承したのに約束ではない」状態になるが、これは以前からの挙動。指摘するなら重大度を下げて
D. **canApprove の doneAttacks**: 3 か所で実凸の数の出どころが違う
   (_resvTransition = 盤面の attackCount / _answerPin = _myPubState.todayAttacks / _reserveForFinishRequest = supabaseLoadMyAttacks)。
   盤面未ロードや _myPubState 未初期化で 0 になると、画面側の検査だけが甘くなる (DB は守る)。**DB より緩い方向にしかズレない**ことを確認。
   逆に**DB より厳しい方向**にズレる経路 (画面が拒否するのに DB は通す) があれば、それは押せない不具合なので指摘
E. **null 契約の取りこぼし**: ea3e036 で null を返すようにした関数の呼び出し側で、まだ `.map` / `.length` / `.filter` を
   null に対して呼ぶ箇所が無いか (TypeError で描画が止まる)。特に _finishReqCache の利用箇所 (index.html で 8 か所) と
   extras の利用箇所 (memberStatus.js / index.html の _mbPaint・summarize・nudge)
F. **テストの穴**: 変異テストは通したが、あなたの目で「このガードは形だけ」と思うものがあれば
G. **CAS の副作用**: `.eq('status','pending')` を付けたことで、正当に pending 以外を更新する経路を壊していないか
