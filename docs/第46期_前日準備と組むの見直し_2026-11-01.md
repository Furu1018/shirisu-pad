## 1. 「何か変更がないと決定が押せない」

### いまの動き (index.html `renderOpsBuild` → `_obDecideRange` / `_obFreshOf`・`_obDecide`)
- 決めるブロック = いまのブロックから、組めた (🧮 した・駒を置いた) ブロックが続くところまで (`decidePlanDomain.rangeToDecide`)。
- そのうち**今回決めるのは「組み直したブロック」だけ** (`_obFreshOf`)。決定から読み戻したまま触っていないブロックは「前の決定のまま写す」(S4 レビュー [2]: 前の決定を黙って上書きしない)。
- 組み直したブロックが 1 つも無いと **✅ 決定 は押せない** (ヒント「決定のあと組み直したブロックはありません (組み直すと決定し直せます)」)。`_obDecide` の中でも同じ理由で止まる。
- 通知は `_obNotifyDecide` が**人ごとの差分** (変わった人・増えた人・外れた人) にだけ送る。

### 困りごと
- 運営は「いまの盤でいい」と確かめたあとに **決定を押して区切りを付けたい**。押せないと「決定されているのか」が分からない (決定済みの表示は小さい)。
- 何か触らないと押せないので、わざと駒を動かして戻す、という操作になる。

### 案
| 案 | 何をするか | 良い | 悪い |
|---|---|---|---|
| A | **組めたブロックがあればいつでも押せる**。組み直していなければ「このまま決定し直す (変更なし)」に文言を変え、同じ中身で決定の行を作る。通知は出さない (Q1) | 操作が一直線。運営が確かめた時刻が残る | 決定の行が増える (中身は同じ・読む側は最新だけ見るので影響なし) |
| B | いまのまま + 「確かめた」ボタンを別に置く | 決定の意味を変えない | ボタンが 2 つ (ボタンの監査で減らしたばかり) |
| C | 変更なしでも押せるが、通知を必ず送る | 伝わる | 変わっていないのに通知が届く = 振り回す |

**提案 = A**。押せないのは「前のブロックを変えたあと、そのブロックを見直していない (stale)」ときだけに絞る (今と同じ理由・今と同じ直し方)。

### 影響範囲
- `index.html`: `_obFreshOf` の結果が空でも押せるように (文言・通知の有無を分ける)。`_obDecide` の「組み直したブロックがありません」の停止を外し、`decidePlanDomain.build` に `newIdxs = range` (全部写し直し) を渡す。
- `js/domain/decidePlan.js`: 変更なし (build は newIdxs が空でない前提のまま)。
- テスト: `tests/run-tests.mjs` の決定の配線 (「組んでいないと決定できない」の検査がある — 文言を合わせる)。

## 2. 「そのブロックしか凸できない人」を先に見る

### いまの動き (`blockBuildDomain.trayPieces` / `canDrop`・`renderOpsBuild`)
- 選んだブロックのピース置き場で、**出られるブロックが 1 つの人は 🔒 が付いて先頭に並ぶ** (`rigid: avail.length === 1`)。置き場の見出しに「🔒 = この時間帯しか出られない人 (先に置く)」。
- ほかのブロックの 🔒 は、そのブロックを開くまで見えない。ブロックのボタンにも出ない。
- 撃破済みのボスの行には置けない (`canDrop`: 「Lv2 で撃破済みです (次のレベルは次のブロックから)」)。レベルが上がるのは **5 体とも撃破したブロックの次のブロックから** (`overview.allDone`)。
- 第46回の実データ: 21 人中 **5 人が 1 つのブロックだけ** — A 朝: NAVI01・翠秋めぐる / D 夕方: MIRIN・銀狐リン / E 夜: イオ (ブロックは既定の 6 つ)。

### 困りごと (ふるりの言葉そのまま)
🔒 の人の凸先のボスが、そのレベルで**前のブロックで撃破される見込み**だと、その人のブロックでは置けない。5 体全部を倒して次のレベルを出すか、そのボスを残しておくかを、**前のブロックを組む時点で**決めておかないといけない。いまは当のブロックを開いて初めて分かる。

### 案
| 案 | 何をするか |
|---|---|
| A | **ブロックのボタンに 🔒 の人数**。置けない見込みがあれば赤 (⚠) |
| B | **🔒 の段を新しく置く** (ブロックのボタンの下・盤の上)。ブロックごとに 🔒 の人・その人の模擬 (属性とダメージ)・見込み (✓ 置ける / ⚠ 相手ボスは前のブロックで撃破見込み・Lv3 は出ない見込み (残り: B1・B4))。⚠ には「C を開く」「B3 Lv2 を C で残す」の近道 |
| C | **ピース置き場で、置けないピースを赤に** (押す前に分かる。押したときの理由は今のまま) |
| D | **🧮 残りを自動で組む に「🔒 の人を必ず置く」の優先度** (前のブロックを組むとき、後ろの 🔒 の人の相手ボスを残す / 5 体倒して Lv を上げる、のどちらかが成り立つように) |

**提案 = A + B + C を先に (見せるだけ・止めない — Q2)。D は使ってみてから。**
見込みの計算は新しくない: 今の `overview` が「前のブロックまでを実行した HP」を出しているので、そのまま 🔒 の人の相手ボスに当てはめる。

### 影響範囲
- `js/domain/blockBuild.js`: 新しい純関数 `lockOutlook({ ov, blocks, players })` — ブロックごとに { 人, 模擬の属性・ダメージ, 相手ボス, 置ける/置けない, 理由 (撃破見込みのブロック・そのレベルの残りボス) }。既存の `trayPieces` の `rigid` と同じ判定を共有 (Q3 の「最後のブロック」を足すならここ)。
- `index.html`: ボタンの人数バッジ・🔒 の段・置けないピースの赤。
- テスト: `tests/run-tests.mjs` に lockOutlook の検査 (置ける / 撃破見込みで置けない / 5 体撃破で次のレベルが出る / 最後のブロックの人)。
- D をやるなら `js/optimal-plan.js` (ソルバー) の優先度 — 大きいので別の回に。

## 3. 前日準備: 人を選んで 5 属性をまとめて入れる (GB のプリセットの応用)

### いまの動き
- 運営 › 👥 メンバー › **📸 模擬の取り込み** の **模擬ダメージ表** (人 × 属性・`mockIntakeDomain.tableRows`)。マスの ＋ → `_opsMockManual` → **1 人 × 1 属性 × 1 編成のモーダル** (`openMyDmgPreviewModal` の手入力: 属性・ダメージ (B)・5 キャラはアイコンをタップして選ぶ (よく使われる順)) → 保存 (`supabaseSaveMockSubmission(playerId, attribute, { damageB, slot, characters, actorName })` → `player_damages` 1 行 + 編成)。
- スクショの取り込みはカードの受け口 (画像を落とす) → 同じモーダル。
- **📚 人気編成** は 模擬タブ の別のカード (`popularTeamsDomain.buildPopularTeams`: 今シーズンの模擬 + 過去の凸の合算・人数順・属性ごと)。入力の画面からは使えない。
- GB (しりすこPAD GB・別リポジトリ `~/Desktop/shirisu-pad-global`) の編成ピッカー: 属性を選ぶと **使用率 TOP の編成がタップで 5 枠に入る** + 枠ごとの候補は今シーズンの採用数順 (GB の `js/app.js` の `compBodyHTML` / `pickerGridHTML`)。

### 困りごと
- 21 人 × 3〜5 属性 = 60〜100 回、モーダルを開いて閉じる。キャラは毎回 5 回タップ。
- 同じ編成を使う人が多い (第46回: 風圧は **22 人が同じ 5 人**・灼熱は上位 2 編成で 12 人) のに、毎回選び直している。

### 案 (モック ②)
1. 模擬ダメージ表の **名前を押す → その人の 5 属性が 1 枚のモーダル** (ボスの順 B1→B5)。見出しに 〆 と 🔒 (出られるブロック)・前回の凸の要約。
2. 属性ごとに **プリセット**: 「前回の自分」(そのレイドの実凸の編成) → 「この属性でよく使われる編成」(📚 と同じ集計・人数と中央値つき・第45/46回の印) → 「自分で 5 キャラを選ぶ」。**押すと 5 枠に入り、ダメージの欄にフォーカス**。
3. ダメージは数字だけ。**入れた属性だけ**を「まとめて保存」(属性ごとに今の RPC を順に・失敗した属性だけ残す — Q5)。「次の人 →」で 〆 の早い順に進む。
4. B5 (18 時以降に出られる人は 2 編成) は属性の中の「＋ 2 編成目」。キャラが被らない編成だけ選べる (今の `dup` の判定を使う)。
5. 🔒 の人は表に印 → **その人の模擬を先に埋める** (② と ①-🔒 のつながり)。

### プリセットの材料 (全部ある)
- 前回の自分: 月次JSON `data/YYYY-MM.json` の `attacks[].characters` (画像パス) → キャラ名。本家の `nikke_characters.icon_paths` で解決 (今日 6 種を紐づけたので**第46回の凸は全部解決できる**)。
- よく使われる編成: `popularTeamsDomain.buildPopularTeams({ mockRows, histRows })` そのまま。
- 表示: 本家はキャラの画像を持っているので顔で出せる (GB は自作タイル)。

### 影響範囲
- `index.html`: 新しいモーダル (1 枚) と、模擬ダメージ表の名前のボタン。保存は今の `handleMyDmgPreviewSave` の保存部分を関数に切り出して属性ごとに呼ぶ。
- `js/domain/mockIntake.js`: `presetsFor({ attr, player, popular, lastRaid })` (並び・重複除去・被りの判定) の純関数。
- 月次JSON: 「前回の自分」の編成は画像パス → キャラ名の解決が要る。📚 人気編成が `buildPopularTeams` の `resolveHist` 引数に渡している無名関数 (index.html・`resolveNikkeChar` でキャラ表から引く) と同じものを使う (新しく書かない)。
- DB: 変更なし。
- テスト: `tests/run-tests.mjs` に presetsFor / 「入れた属性だけ保存」の検査。モーダルの描画は `tests/mock-panels.mjs` の型で実行テスト。
