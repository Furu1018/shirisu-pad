## 1. 「何か変更がないと決定が押せない」

### いまの動き (index.html `renderOpsBuild` → `_obDecideRange` / `_obFreshOf`・`_obDecide`)
- 決めるブロック = いまのブロックから、組めた (🧮 した・駒を置いた) ブロックが続くところまで (`decidePlanDomain.rangeToDecide`)。
- そのうち**今回決めるのは「組み直したブロック」だけ** (`_obFreshOf`)。決定から読み戻したまま触っていないブロックは「前の決定のまま写す」(S4 レビュー [2]: 前の決定を黙って上書きしない)。
- 組み直したブロックが 1 つも無いと **✅ 決定 は押せない** (ヒント「決定のあと組み直したブロックはありません (組み直すと決定し直せます)」)。`_obDecide` の中でも同じ理由で止まる。
- 通知は `_obNotifyDecide` が**人ごとの差分** (変わった人・増えた人・外れた人) にだけ送る。

### 困りごと
- 運営は「いまの盤でいい」と確かめたあとに **決定を押して区切りを付けたい**。押せないと「決定されているのか」が分からない (決定済みの表示は小さい)。
- 何か触らないと押せないので、わざと駒を動かして戻す、という操作になる。

### 案
| 案 | 何をするか | 良い | 悪い |
|---|---|---|---|
| A | **組めたブロックがあればいつでも押せる**。組み直していなければ「このまま決定し直す (変更なし)」に文言を変え、同じ中身で決定の行を作る。通知は出さない (Q1) | 操作が一直線。運営が確かめた時刻が残る | 決定の行が増える (中身は同じ・読む側は最新だけ見るので影響なし) |
| B | いまのまま + 「確かめた」ボタンを別に置く | 決定の意味を変えない | ボタンが 2 つ (ボタンの監査で減らしたばかり) |
| C | 変更なしでも押せるが、通知を必ず送る | 伝わる | 変わっていないのに通知が届く = 振り回す |

**提案 = A**。押せないのは「前のブロックを変えたあと、そのブロックを見直していない (stale)」ときだけに絞る (今と同じ理由・今と同じ直し方)。

### 影響範囲
- `index.html`: `_obFreshOf` の結果が空でも押せるように (文言・通知の有無を分ける)。`_obDecide` の「組み直したブロックがありません」の停止を外し、`decidePlanDomain.build` に `newIdxs = range` (全部写し直し) を渡す。
- `js/domain/decidePlan.js`: 変更なし (build は newIdxs が空でない前提のまま)。
- テスト: `tests/run-tests.mjs` の決定の配線 (「組んでいないと決定できない」の検査がある — 文言を合わせる)。

## 2. 「そのブロックしか凸できない人」を先に見る

### いまの動き (`blockBuildDomain.trayPieces` / `canDrop`・`renderOpsBuild`)
- 選んだブロックのピース置き場で、**出られるブロックが 1 つの人は 🔒 が付いて先頭に並ぶ** (`rigid: avail.length === 1`)。置き場の見出しに「🔒 = この時間帯しか出られない人 (先に置く)」。
- ほかのブロックの 🔒 は、そのブロックを開くまで見えない。ブロックのボタンにも出ない。
- 撃破済みのボスの行には置けない (`canDrop`: 「Lv2 で撃破済みです (次のレベルは次のブロックから)」)。レベルが上がるのは **5 体とも撃破したブロックの次のブロックから** (`overview.allDone`)。
- 第46回の実データ: 21 人中 **5 人が 1 つのブロックだけ** — A 朝: NAVI01・翠秋めぐる / D 夕方: MIRIN・銀狐リン / E 夜: イオ (ブロックは既定の 6 つ)。

### 困りごと (ふるりの言葉そのまま)
🔒 の人の凸先のボスが、そのレベルで**前のブロックで撃破される見込み**だと、その人のブロックでは置けない。5 体全部を倒して次のレベルを出すか、そのボスを残しておくかを、**前のブロックを組む時点で**決めておかないといけない。いまは当のブロックを開いて初めて分かる。

### 案
| 案 | 何をするか |
|---|---|
| A | **ブロックのボタンに「このブロックのみ N 人」**。置けない見込みがあれば赤 (⚠) |
| B | **「このブロックのみ / このブロックで最後」の段を新しく置く** (ブロックのボタンの下・盤の上)。ブロックごとにその人・模擬 (属性とダメージ)・見込み (✓ 置ける / ⚠ 相手ボスは前のブロックで撃破見込み・Lv3 は出ない見込み (残り: B1・B4))。⚠ には「C を開く」「B3 Lv2 を C で残す」の近道 |
| C | **ピース置き場で、置けないピースを赤に** (押す前に分かる。押したときの理由は今のまま) |
| D | ~~🧮 残りを自動で組む に「必ず置く」の優先度~~ — **採らない** (Q2・ふるり「ルールに引っ張られて総合スコアが減るときもある」) |

**決まり = A + B + C (見せるだけ・止めない — Q2)。D はやらない。印は 🔒 でなく文字 (Q3)。**
見込みの計算は新しくない: 今の `overview` が「前のブロックまでを実行した HP」を出しているので、そのまま 🔒 の人の相手ボスに当てはめる。

### 影響範囲
- `js/domain/blockBuild.js`: 新しい純関数 `lockOutlook({ ov, blocks, players })` — ブロックごとに { 人, 種類 (only = このブロックのみ / last = このブロックで最後), 模擬の属性・ダメージ, 相手ボス, 置ける/置けない, 理由 (撃破見込みのブロック・そのレベルの残りボス) }。既存の `trayPieces` の `rigid` と同じ判定を共有し、「最後」を足す。画面の文字は「このブロックのみ」「このブロックで最後」(🔒 は使わない — Q3)。

## 5. 結果から: 属性ごとに「その属性で選ばれてきたボス」へダメージが出やすかった編成 (本家 + GB)

### いまあるもの
- **🌏 GB比較 › 編成** (`renderGbCompare` / `js/domain/gbCompare.js` `filterComps`): GB の凍結エクスポート (`data/gb-export/<month>.json`) から、属性ごとに **人気 (人数順) / 強い (中央値順) / 強い且つ人気** を出せる。材料は GB だけ (ユニオンの凸は出ない)。本家にあるのは 2026-08・2026-09 で、**2026-10 の凍結版は GB 側にあるがまだ本家にコピーしていない**。2026-11 は GB のシーズンが終わってから `export-season.mjs` → コピー。
- **📚 人気編成** (模擬タブ・いまは隠れている): 編成の人数順。「ダメージ順は SLv が高い人の編成が上に来るだけで参考にならない」(ユーザー決定 2026-08-11) ので並びは人気だけ (`popularTeamsDomain`)。
- **🛡 全体分析** (`raidReview.js`): 属性別の進捗・得意不得意 (1 凸あたりの対 GB 中央値比・SLv 補正・締め凸除く)・誰がどの属性で — **人別**で、編成別は無い。

### 困りごと
「水冷なら、水冷で選ばれてきたボス (トゥームストーン・ドリアン・ブラックスミス…) に、どの編成が効いたか」を、ユニオンの実凸と GB の提出の**両方を同じ物差し**で、**回をまたいで**見る画面が無い。本家はボスのコード (H.S.T.A. など `BOSS_ATTRIBUTES`) と PT 属性が固定なので、同じコードのボスを回またぎで集めれば「その属性で選ばれるボス」になる。2026-08-11 の判断 (ダメージ順は参考にならない) は **SLv 補正無し**の話で、SLv 600 換算にそろえれば比べられる (🛡 全体分析と GB比較がすでにその換算をしている)。

## 6. ブロックの間に「再編成時間」を置く (2026-11-02 ふるり・ユニオンの意見)

> ふるり (11/2):「例えば 12:45〜13:00 を再編成時間にして、その間で次のブロックの編成を組みたい。2 時間前だと予測値と実測値がズレすぎて、あんまりプランとして機能しなかった」
> 「今後はブロックとブロックの間に運営のプラン再編成の時間を設けて、A ブロック → B の編成の時間 → B ブロック のようにしたい。そうすれば模擬も直前までやれる」

### いまの作りとの相性
- ブロックは **5 時〜翌 4 時を隙間なく・1 時間刻み・2〜12 個** で持っている (`raidBlocksDomain.normalize`: 「前に隙間か重なりがあります」で止まる・`toHour` は時)。
  → **隙間のブロックは作れない**し、15 分は 1 時間刻みに乗らない。再編成時間は**「各ブロックの最後の N 分は凸しない時間」という決めごと**として持つのが自然 (ブロックの区切りはそのまま)。
- 運営の手順はもうブロックの頭ごとに並んでいる (`planBoardDomain.blockSteps`: ⚔️ HP を直す → 📥 結果を取り込む → 🧱 組む → ✅ 決定 → 🏁)。再編成時間は、この手順に**時間の枠を与える**だけで、新しい流れではない。
- 「Lv はブロックの頭でしか上がらない」とも合う: 再編成時間に 5 体倒れていれば次のブロックは次の Lv、倒れていなければ同じ Lv の残り、と**実測で**決まる。
- 時刻の例 (既定 6 ブロック・20 分): A の凸は 5:00〜8:40 → 8:40〜9:00 再編成 → B 9:00〜12:40 → 12:40〜13:00 → C 13:00〜16:40 → 16:40〜17:00 → D 17:00〜20:40 → 20:40〜21:00 → E 21:00〜翌0:40 → 翌0:40〜1:00 → F 翌1:00〜5:00 (最後のブロックの後ろに再編成は無い)。A の前 (〜5:00) は前日〜朝の組みで決める。
- メンバー向けの絵 (ChatGPT) のプロンプト: `docs/ChatGPT画像プロンプト_ブロック制_2026-11-02.md`
- 模擬の 〆 (`mockIntakeDomain.deadlineOf` = 最初に出られるブロックの前) は、そのまま「最初に出られるブロックの再編成時間の始まりまで」と読み替えればよい。

### 15 分でできるか (運営が再編成時間の中でやること)
1. ⚔️ 🎯 ボス HP を更新 (BlaBlaLINK のスクショ 1 枚・読み取りと差分の確認) — 2〜3 分
2. ✓ 凸の記録 (Discord のスクショを見て名前の札を押す) — 人数しだい・前のブロック中に随時やっておけば 1〜2 分
3. 📸 遅れて届いた模擬の登録 (③ の 1 人 5 属性モーダルができれば短い) — 0〜5 分
4. 🧱 組む (🧮 + 「このブロックのみ」の人の確認) → ✅ 決定 — 3〜5 分
5. メンバーが通知を見て 📅 レイド予定表で ✅ — 決定から数分
→ 全部そろっていれば 15 分で足りるが、**余裕は無い**。最初は **20〜30 分**で試し、慣れたら縮めるのが安全。遅れて再編成時間に入った凸は HP をずらすので、「終わらなかった凸は次のブロックに回す」と決めておく。
