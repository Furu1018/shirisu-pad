# 通知の見える化 — 設計案 (2026-10-08・検討段階・未実装・Codex レビュー済み)

ユーザー (運営ふるり) の要望:
1. メンバーがスマホ等の**端末で通知を設定できているか**を知りたい
2. 運営の送ったメッセージを**見ていないのか、見たうえで反応が無いのか**を分けたい (既読確認)
3. **アプリの更新情報**をお知らせする欄がほしい

まず仕組みを検討する。10/10 のレイドは凍結中なので、着手はレイド後。Codex に設計レビューを依頼し (2026-10-08)、指摘を §7 に、反映後の案を §3〜§6 に書いた。

## 0. いまの 🔔 (運営タブ › メンバー状況) の意味

`memberStatusDomain.buildRows` + `_mbPaint` (index.html) が、`push_subscriptions` に**その人の行があるか**だけで決めている:

| 表示 | 意味 | 出どころ |
|---|---|---|
| 🔕 (赤) | `push_subscriptions` にその人の行が **1 つも無い** = どの端末でも通知を有効にしていない | 行の有無 |
| 🔔 (薄い) | 行がある (= いつかどこかの端末で「通知を有効にする」を押した)。疎通確認はまだ | 行の有無 |
| 🔔 未確認 | 今期の疎通確認を送ったが、本人がタップも「届きました」も押していない | `raid_event_notices` kind `push_check_sent` / `push_check` |
| 🔔✓ | 今期の疎通確認が届いたと本人が伝えた | 同上 |
| 🔔? | 購読の一覧を取得できなかった | 通信エラー |

**混在の正体 (2026-10-08 の実データ)**: 在籍 31 人のうち **26 人に行があり (🔔)、5 人に無い (🔕: みに / パン / イオ / ヤマト / KAGETORA)**。
10/7 まであった「アプリの中の通知 OFF」は**解除 = 行の削除**だったので、過去に解除した人も、一度も有効にしていない人も、
Push サービスが 410 を返して消された人も、すべて同じ 🔕 になる (区別はできない)。10/7 以降は「通知 OFF」という操作が無いので、
🔕 を消す方法は**本人が端末で「通知を有効にする」を押す**ことだけ。今期 (2026-10) の疎通確認はまだ送っていないので、🔔 未確認 / 🔔✓ は出ていない。

**🔔 の限界**: 行がある ≠ いま届く。42 行のうち 22 行は 2026-07 より前に作られたもので、端末を変えた・PWA を消した・OS が購読を失効させた人は
**次に送ったとき 410 が返って初めて**行が消える (Edge Function `send-push` が 410/404 で削除)。端末の通知許可 (OS の設定) はサーバからは見えない。
「届いた・見た」が分かるのは、いまは疎通確認の**タップ**だけ。
→ 🔔 の title は「通知は有効」ではなく **「購読の登録あり (届くかは未検証)」** に直すべき (Codex指摘 H)。

## 1. 要望を信号に分ける (1 人 × 1 通) — 言えること / 言えないこと

| 信号 | 言えること | 言えないこと | いま | 案 |
|---|---|---|---|---|
| **送った** (accepted / expired) | Push サービスが受理した / 購読が失効していた | 端末に出た・見た | 件数だけ (`sent_count`) | 端末 (購読) ごとに残す |
| **端末受信記録** (device_report) | その端末の Service Worker が動いて記録まで完走した | 本人が見た (おやすみモードでも記録される) | 無い | SW の `push` から記録 (**ベストエフォート**。無い = 分からない) |
| **開いた** (opened) | 通知をタップした / アプリの通知一覧で既読にした | 内容を読んだ | 疎通確認のタップだけ | SW の `notificationclick` + アプリ内の既読を記録 |
| **反応した** (acted) | その通知が求める操作が済んだ | 通知を見て操作したという因果 | 機能ごとに既にある | 第二段 (通知と操作の結び付けは膨らむ) |

運営が知りたい 3 つは、**言い切れる範囲**でこう言う (Codex指摘 C: 文言は「記録なし / 確認できず / 反応未確認」に統一):
- **端末に届かない可能性が高い人** = 購読なし / 送ったら失効 (410) だった / 最後に開いた端末で通知が「拒否」
- **見た記録が無い人** = 開いた も 端末受信記録 も無い (「見ていない」と断定しない)
- **見たが反応が無い人** = 開いた (タップ or アプリ内既読) があり、反応した が無い。端末受信記録だけなら「受信記録あり・反応未確認」止まり

## 2. 設計の前提 (変えない)

- RLS anon 全許可・名乗りは自己申告 (内輪運用)。新しい表もその流儀
- 通知の宛先は `js/domain/notifyPolicy.js` が唯一 (あなた宛 / チームの状況 / テスト)。ここは触らない
- サーバ側の cron は無い (運営端末の定期チェックが送り手)
- iOS は 16.4 以降・ホーム画面に追加した PWA だけ Web Push が使える。push を受けたら必ず `showNotification` する
- ★ **Edge Function `send-push` は変えざるを得ない** (Codex指摘 B): いまの payload は `{title, body, url, tag, requireInteraction}` で `data` を通さず、
  端末ごとの `results` は `push_subscriptions.id` しか返さない (player_id も endpoint も無い)。変更は**まとめて 1 回**の再デプロイにする

## 3. 仕組み (Codex レビュー反映後)

### A. 通知に id を付ける
- 送る前に**クライアントで uuid (`nid`) を作る** (`crypto.randomUUID()`)。`sendPushNotification` は Edge Function を呼ぶ前に
  `push_notifications_log` へ `nid` つきで insert し (= **通知本体の行は送信前に作る**。Push が先に着いて記録が nid を参照できない競合を無くす)、
  送ったあとに `sent_count` と端末ごとの結果を書く
- Edge Function: payload に `data: { nid }` を通す。`results` に `player_id` を足す (`{ id, player_id, ok, removed, error }`)

### B. 3 つの表に分ける (Codex指摘 B: 人単位に潰さない)
1. **通知本体** = `push_notifications_log` に `nid uuid UNIQUE` と `target_player_ids` のスナップショット (既存列)
2. **送信対象の端末** = 新表 `push_targets (nid, subscription_id, player_id, result 'accepted'|'expired'|'error', at)`、一意 `(nid, subscription_id)`。
   Edge Function の `results` から `sendPushNotification` が書く (購読が 410 で消えても、**送信時点の購読 id と人**が残る)
3. **端末の報告** = 新表 `push_reports (nid, subscription_id, player_id, kind 'received'|'opened', at)`、一意 `(nid, subscription_id, kind)`。
   RPC `record_push_report(p_nid, p_endpoint, p_kind)` (SECURITY DEFINER) が endpoint → `push_subscriptions (id, player_id)` を引いて insert。
   SW は自分の player_id を知らないが endpoint は `self.registration.pushManager.getSubscription()` で分かる
- 画面は人単位に集約する (「どれかの端末で受信記録あり」)。保存は端末単位 (iPhone は受信・PC は失効、を後から説明できる)

### C. Service Worker (`sw.js`)
- `push`: `event.waitUntil(showNotification(...).then(() => report('received')))` — **1 つの waitUntil で両方を待つ**。失敗は黙って捨てる
- `notificationclick`: 既存の遷移を**遅らせない** (報告は `waitUntil` で並走させ、遷移は先に)。kind `opened`
- anon キーは `sw.js` に書く (クライアントに公開前提の値。payload に毎回載せる利点は無い: Codex指摘 A)
- ★ 取りこぼしは**設計値として見積もれない** (iOS は SW をすぐ止める)。「無い = 分からない」で扱う。より確実にするなら、失敗した報告を
  SW の IndexedDB に残して次の起動時に再送 (第二段)

### D. 端末の状態 (「本体で設定しているか」) — 要望①に最も直接的。**先に作る** (Codex指摘 E・G)
- 新表 `member_devices (device_id, player_id, ua, push_permission 'granted'|'denied'|'default'|'unsupported', subscription_id (その端末の購読。無ければ null),
  app_build, reported_at, last_seen_at)`、主キー `device_id`
- `device_id` は端末の localStorage の乱数 (**恒久ではない**: 再インストール・サイトデータ削除で変わる → 古い行は `last_seen_at` が止まるだけ)
- 起動時と名乗り直しに upsert。**書き込みの抑制 (1 端末 1 時間に 1 回) と `last_seen_at` の意味を分ける**: `reported_at` = 最後に報告した時刻、
  `last_seen_at` = アプリを最後に開いた時刻 (抑制中は端末の localStorage に持ち、次の報告でまとめて送る)
- **名乗り直し**: 同じ端末が別の人の行として残らないよう、`device_id` を主キーにして上書き (いまの名乗りだけが残る)
- `subscription_id` は**その端末の購読 (endpoint)** と結び付ける (別端末の古い購読と矛盾させない)
- 運営の見え方: 「最後に開いた端末 (iPhone / Android / PC) で通知が 許可 / **拒否** / 未設定」「最後に開いた日時」「アプリの版」。
  ★ `app_build` は互換ゲート (41) を締めるときの**観測値** (移行の進み具合) であって、「全員更新済み」の証明ではない (未起動の端末は見えない)。
  ゲートは引き続き版の判定で閉じる

### E. 運営の見え方
1. **メンバー状況の 🔔 列**: 1 つのアイコンに押し込まず、**優先順位を明文化**して出す (Codex指摘 D):
   ① 🔕 購読なし → ② 🔔⚠ 送ったら失効 / 最後に開いた端末で「拒否」(別端末に生きた購読と受信記録があれば ⚠ にしない) →
   ③ 🔔✓ 今期の疎通確認を本人が確認した (既存のタップ式。**残す**) → ④ 🔔◦ 直近 30 日に端末受信記録あり (本人確認はまだ) →
   ⑤ 🔔 購読の登録あり (届くかは未検証) / 🔔 未確認 (疎通確認を送ったが本人確認なし・受信記録なし)。
   「未着」とは書かない (「記録なし」「確認できず」)
2. **通知ごとの内訳** (運営タブ › その他 › メンテナンス › メンバーの通知状況 を拡張): 1 通ごとに 送 n / 受信記録 n / 開いた n と、
   **届かない可能性が高い / 見た記録なし / 開いたが反応未確認** の名前の 3 列。全員あての通知は `target_player_ids` のスナップショットで分母を固定
   (新規加入・購読なしの人を「未着」に混ぜない)。「Discord 用にコピー」は既存のものを流用
3. **反応した との結び付け** (締め凸の返事・📣 の返事・✅ 確認しました) と 🔁 直近の動きの「見た / まだ」の印は**第二段** (通知と操作の因果を正しく結ぶ設計が要り、膨らむ: Codex指摘 G)
4. 本人側: 変えない。**既読が運営担当に見えることはヘルプ §13 に明記**する

### F. アプリの更新のお知らせ (Codex: 問題なし)
- `data/release-notes.json` を**リリースごとに私が書く** (`{ id, build, date, title, lines[] }` をメンバー向けの言葉で)。CLAUDE.md に「画面が変わる commit には 1 項目足す」をルール化
- ホームに **🆕 新しくなったこと** カード: 端末が最後に見た **`id`** (日付や文言ではなく不変の id。並べ替え・文言修正で再表示が壊れないように) より新しいものだけ出し、畳める。ヘルプに「更新履歴」章
- 大きい変更は運営が「チームの状況」の通知で一言 (任意・既存の一斉送信)
- DB は要らない。運営が**任意の時刻に投稿・固定・編集**したくなったら `announcements` 表を第二段で

## 4. 穴と割り切り

- **端末受信記録 ≠ 見た**: OS が「おやすみ」でも push イベントは走る。だから 開いた / 反応した と分け、文言を「反応未確認」に留める
- **SW の記録は取りこぼす**: 「記録なし」は「分からない」として扱い、断定の文言にしない。開いた / 反応した があれば受信記録が無くても「見た」に倒す
- **PC のブラウザ通知**は通知センターに溜まるだけで気づかれにくい → 受信記録はあるが開いていない、が普通に起きる
- **同じ `tag` の通知は置き換わる** (古い通知が消える) → 開く機会が無いまま「開いていない」になる
- **既読の可視化**はメンバーに伝えてから。見えるのは運営担当だけ
- `push_targets` / `push_reports` は増え続ける → 90 日より古い行は運営の「終了」チェックリスト (バックアップ保存) のついでに消す。23 の restore helper と `_BACKUP_TABLES` に足すかどうかはそのとき決める
- 練習モード (`js/practice/server.js`) は SQL の写しなので、表を足したら写しも足す (`tests/practice.mjs` が突き合わせる)

## 5. 作る順 (Codex と合意した小さく始める順)

1. **F 更新履歴** — レイドに関係なく、DB も Edge Function も要らない。**10/10 の前に入れてもよい**
2. **D `member_devices`** — 要望①の本体。SQL 1 本 + 起動時の upsert + メンバー状況の 🔔⚠ (拒否) と「最後に開いた」。Edge Function 不要
3. **A + B-1/B-2 nid と送信対象の端末** — `push_notifications_log.nid` / `push_targets` / Edge Function の再デプロイ (payload の `data.nid`・results の player_id)。
   既存のタップ式 疎通確認は**そのまま**。🔔 列に「送ったら失効」が出せるようになる
4. **C + B-3 + E-2 SW の受信記録・開いた・通知ごとの内訳** — ここで初めて「見た記録なし / 開いたが反応未確認」が言える
5. (第二段) 反応した との結び付け・🔁 の印・SW の再送・announcements

10/10 のレイドは**いまの疎通確認 (タップ式)** で運用する。
